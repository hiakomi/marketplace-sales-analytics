# Аналитика продаж маркетплейса

**Python · PostgreSQL · SQL · Metabase**

Учебный проект: получение данных о продажах через API, историческая и ежедневная загрузка в PostgreSQL, исследование ассортимента и клиентской базы.

Ассортимент исследуется с помощью двойного ABC и XYZ. Клиентский анализ включает RFM, месячный retention, повторную активность и накопленную выручку на клиента. Аналитический период — **2023 год**.

## Какие вопросы решает проект

| Направление | Вопрос | Метод |
|---|---|---|
| Ценность ассортимента | Какие товары формируют выручку и объём продаж? | ABC по выручке и количеству единиц |
| Вариативность спроса | Насколько различаются месячные продажи товаров? | XYZ по коэффициенту вариации |
| Ассортиментное ревью | Какие SKU требуют дополнительного рассмотрения? | ABC-XYZ и отбор внутри CCZ |
| Скидки | Как размер скидки связан с объёмом продаж? | Группировки и корреляции |
| Ценность клиентов | Какие группы отличаются давностью, частотой и суммой покупок? | RFM |
| Повторная активность | Возвращаются ли клиенты и как быстро? | Когорты, retention, repeat rate |
| Денежные показатели | Как накапливается выручка на клиента? | Наблюдаемый выручечный LTV |
| Сценарии | Какой дополнительный оборот соответствует росту M1-retention? | Условная оценка при постоянной выручке на активного клиента |

## Как работает загрузка

Скрипт запрашивает API за конкретную дату, создаёт DataFrame и приводит `purchase_datetime` к календарной дате. Затем подключается к PostgreSQL и выполняет `DELETE` за запрошенный день и пакетный `INSERT` внутри одной транзакции. При ошибке записи изменения откатываются.

При последовательном повторном запуске непустая дневная выгрузка заменяет прежнюю. Пустой ответ API пропускается: уже сохранённые данные за этот день остаются. Одновременные загрузки одной даты не защищены от конкуренции.

`total_price` загружается из API и приводится к `float`; эти скрипты не пересчитывают его из цены, скидки и количества.

## Запуск

Нужны Python, доступ к API и существующая PostgreSQL-база с таблицей `sales`.

```bash
git clone https://github.com/hiakomi/marketplace-sales-analytics.git
cd marketplace-sales-analytics
python -m venv .venv
```

Активируйте окружение и установите зависимости:

```bash
# Linux / macOS
source .venv/bin/activate
pip install -r requirements.txt
```

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Задайте `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` в окружении процесса. Примеры для обеих систем и требования к таблице находятся в [инструкции](docs/setup.md). Скрипты **не читают `.env` автоматически**.

```bash
# Историческая загрузка за 2023 год
python load.py

# Данные за вчера
python daily_load.py
```

Затем выполните нужный SQL-файл в DBeaver или Metabase. Сами SQL-запросы не зависят от Python.

## Методология

- Аналитическая выборка: `quantity > 0`, даты от `2023-01-01` включительно до `2024-01-01` исключительно.
- ABC: классы по накопленной доле 80% / 95%, отдельно для выручки и количества единиц.
- Итоговый XYZ: CV ≤ 55% — X; 55% < CV ≤ 75% — Y; CV > 75% — Z. Месяцы без продаж включены с нулём.
- RFM: дата расчёта 01.01.2024; F — число уникальных покупательских дней, M — выручка.
- LTV M0–M6: фиксированные когорты января–июня 2023 года, семь месячных точек с учётом M0.
- Repeat rate: возвращение в другой день в течение 30, 60 или 90 дней; для каждого срока учитывается полный горизонт наблюдения.

Без `order_id` покупательские дни нельзя приравнивать к заказам. Выручка не равна прибыли. Сценарный эффект retention не является прогнозом или доказанным причинным эффектом.

## Текущая комплектация

В этой версии опубликованы загрузчики и аналитические запросы из предоставленных исходников. Скриншоты дашбордов, полный отчёт, фактическая DDL-схема, Docker-конфигурация и расписание запуска будут добавлены отдельно. Поэтому полное развёртывание проекта с нуля пока не описано как проверенное.

При оформлении выполнены локальные проверки Python, структуры SQL-файлов и отсутствия исходных реквизитов подключения. API, рабочая база и аналитические результаты в рамках этой подготовки не запускались и не пересчитывались.
